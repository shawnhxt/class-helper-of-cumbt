## 本次改动（v1.9.0）—— 接龙到点关门 + 删掉「打勾叉」+ 选择项全铺成一排

**数据库表结构没有变**（列一个没加、一个没删），只改了取值与行为：
把 `db.py` / `main.py` / `classroot/*.html` / `static/*` 覆盖上去、重启项目即可。
启动时 `db._migrate()` 会把旧库里配成 `check`（打勾叉）的事项改写成 `text`，
**旧库升级无需手工 SQL**。

| 需求 | 实现 |
|---|---|
| 接龙时间过后拒绝继续接龙 | 截止时间一过就不再收新的报名，三道一起收口：① **接口**（`db.add_rollcall` → 400 +「接龙已于 10-02 18:00 截止，不再接受新的报名」）② **接龙页**：报名表单整块不渲染，换成一条截止说明（名单与「复制接龙结果」照旧，班委正是照着名单办事）③ **首页卡片**：提示由「点击卡片进入接龙」改成中性的「接龙已截止，点击查看名单」（灰色虚线胶囊），卡片仍可点进去看名单。**判定只有一个来源**：`db.rollcall_open()` —— 没填截止时间的事项永远开着；填了就认截止时间。**撤销不受影响**（那是纠错，不是新的报名）。注意接口那道是必须的：同学可能在截止前就打开了页面，截止后才点提交，只藏表单拦不住 |
| 删去接龙附加内容「打勾叉」类型 | `ROLL_NOTE_MODES` 由 `("text", "check", "select")` 收成 `("text", "select")`，管理页下拉不再出现「打勾叉」，接口收到 `check` 一律 400（未知的附加信息类别）。原来勾叉只是"√ / × 二选一"，用「进行选择 + 两个候选项」就能表达，留着反而多一个要理解的概念。旧库里配成 `check` 的事项在启动迁移时**回退成 `text`**（报名页变成一个普通文本框），而**名单里已经存下的 √ / × 属于历史数据，原样保留**、照常展示与复制 |
| 「进行选择」直接显示所有选项，优先一行、放不下自动换行 | 报名页那一栏从**下拉框**改成**一排直接能点的胶囊**（原生 radio，选中态画在胶囊上）：选项少的时候点一下选中，不用先点开下拉框；容器是 `flex-wrap`，**优先排成一行，一行放不下（选项多 / 屏幕窄）才自动换到下一行**。每颗的宽度由文字决定且**不压缩**（`flex: 0 0 auto`）—— 留了 `flex-shrink` 的话，一行放不下时浏览器会把每颗都挤窄去迁就，永远换不了行；单个超长选项（上限 20 字）由 `max-width: 100%` 兜住，让文字在胶囊里自己折行。非必填时第一颗是「不填」并**默认选中**（对应 `note = ""`），必填时一颗都不预选，空着提交会被前端与接口拦下 |

### 数据库变更（v1.9.0）

**没有加列、没有删列**，只有一次数据改写：

- `UPDATE notices SET roll_note_mode = 'text' WHERE roll_note_mode = 'check'` ——
  由 `db._migrate()` 在启动时执行，MySQL / SQLite 两种后端都会跑（重复执行无副作用）；
- `rollcalls.note` 里已经存下的 `√` / `×` 不动：它们是当时的报名内容，
  按"附加信息就是一个字符串"的既定规则原样展示、原样导出；
- 想自己确认迁移结果：
  ```sql
  SELECT id, title, roll_note_mode FROM notices WHERE roll_note_mode = 'check';  -- 应当是空结果
  ```

### 关于「截止后还能撤销」

本次只拦**新的报名**。截止后你的报名记录仍然能撤销 —— 那是纠错（名字打错、
临时发现自己报重了），不是新的报名；接龙页上「撤销」按钮的位置与行为都没变。
如果希望连撤销也一起冻结（名单彻底定稿），改起来是一行的事：
`main.py` 的接龙页把 `roll_open` 一并传给名单区、`rollcall.html` 里按它隐藏 `.rc-cancel`，
再在 `db.cancel_rollcall` 里加一道 `rollcall_open` 判断即可。

### 三项设置在数据库里怎么存

`notices` 表新增 4 列，都由 `_notice_fields` 与新增/修改**共用同一套校验**：

| 列 | 类型 | 说明 |
|---|---|---|
| `roll_note_label` | VARCHAR(32) / TEXT | 附加信息名称，留空回退成「附加信息」，最长 16 个字 |
| `roll_note_mode` | VARCHAR(16) / TEXT | `text` 输入文本 / `check` 打勾叉 / `select` 进行选择，非法值一律拒绝 |

### 复制按钮为什么要写两套剪贴板实现

线上是**普通 http**（不是 https、也不是 localhost），此时 `navigator.clipboard` 在浏览器里根本不存在
（它只在安全上下文可用）。所以 `rollcall.html` 里先试 `navigator.clipboard.writeText`，
失败或不支持时回落到「临时 textarea + `document.execCommand('copy')`」。
只写前者的话，线上点按钮会一直提示"复制失败"。

另外复制内容是从**页面 DOM 现读**的（而不是再注入一份 JSON），所以所见即所复制：
刚提交完刷新回来，复制到的就是最新名单。

### 接龙是怎么认人的（没有账号体系）

项目没有登录，所以「我接龙了没有」靠**设备**而不是人来认：

1. 提交接龙时后端发一个 `rc_token`（`secrets.token_urlsafe(16)`）写进 cookie（`HttpOnly` + `SameSite=Lax`，有效约 13 个月）；
2. 每次渲染首页/列表，用这个令牌去 `rollcalls` 表查「本设备报过哪些事项」，命中就标 `joined`；
3. **名单本身对所有人可见**（人数、姓名都来自数据库），令牌只影响"我这条显示成已接龙"。

因此：换手机、清 cookie、用无痕窗口，都会认不出你之前接过龙（但名单还在，名字也在，重新点一下会提示「已经接龙过了」）。
「已接龙」是按**事项**算的：接龙成功的那一刻起，这条在你这台设备上就是「已完成」，不再倒计时。
同一台设备可以替同学/家人代报（填对方姓名即可），**同名同事项只能报一次**。

### 置顶机制要点（`db.py`）

- `level` 仍是实时计算，但置顶优先：`pinned=1` 时 `level` 直接定为 `pinned`，不再按截止时间降级成 `done`。
- 折叠分区把置顶项排除在外：
  - 已折叠 = 截止时间已过阈值 **且未置顶**
  - 未折叠 = 截止时间未过阈值，或没有截止时间，**或已置顶**
  这样置顶的过期事项始终留在主列表，不会从两个列表里同时消失。
- 排序：置顶最优先（多条置顶按 id 倒序），其余仍按截止时间由近到远、已完成沉底。

### 数据库变更（v1.4.0）

`notices` 表新增 `pinned` 列（MySQL `TINYINT`、SQLite `INTEGER`，均默认 0）。
`db.py` 的 `_migrate()` 启动时自动补列并回填旧行为 0，**旧库升级无需手工执行 SQL**。
SQLite 不允许给已有数据的表加「带默认值的 NOT NULL」列，故先加可空列再 `UPDATE ... SET pinned=0`。

### 顺带修掉的一个 MySQL 隐患

折叠区的判定条件原本在模块加载时就把占位符拼进了字符串常量。但 `PH` 要等 `init_db()`
之后才从 `?` 变成 `%s`，于是 MySQL 后端下会带着 `?` 去执行，占位符对不上直接报错
（表现又是「SQLite 正常、MySQL 挂」）。已改成运行时用函数拼接，两种方言都正确。

### 前后端算法一致性

客户端倒计时的级别判定与文案格式，和后端 `compute_level` / `_duration_text` 是同一套规则。
阈值（紧急小时数、秒级精度分钟数、折叠天数）全部由后端通过 `window.CLASS_CONFIG` 注入，
前端不再各写一份数字。已用 node 逐项实测两端输出一致（含 24h/72h 边界、10 分钟精度切换、
过期方向）。

### MySQL 下 admin 列表空白（已修复）

现象：连上 MySQL 后管理页最下面的事项列表一片空白，但降级到 SQLite 时正常，且首页一直正常。

根因是 `_enrich()` 只把 `deadline` 转成了字符串，**漏了 `created_at`**：

| | `created_at` 的类型 |
|---|---|
| MySQL（`TIMESTAMP` 列） | pymysql 返回 Python `datetime` **对象** |
| SQLite（`TEXT` 列） | 返回字符串 |

`/api/notices` 走 `JSONResponse`（底层 `json.dumps`），`datetime` 不可序列化 → 抛 `TypeError` → 接口 500 → 列表区拿不到数据就空白。
首页是 Jinja 服务端渲染，直接 `str()` 输出，所以只有 admin 受影响。

修复：`_enrich()` 统一转换日期时间列；另加 `db.json_dumps()`（带 `default` 兜底，覆盖 `datetime` / `Decimal` / `bytes` / `timedelta`），
`main.py` 所有 JSON 响应改走它。**以后往表里加任何新列都不会再踩这个坑。**

顺带修了两个 SQL 缺陷：
- `list_active` / `count_active` 的 `WHERE deadline IS NULL OR deadline > ? AND category = ?`
  缺括号。SQL 里 `AND` 优先级高于 `OR`，会被解析成
  `deadline IS NULL OR (deadline > ? AND category = ?)`，
  **导致分类过滤对所有未填截止时间的事项失效**——一条没填截止时间的通知会同时出现在三个栏目里。已加括号。
- SQLite 的 `created_at` 没有默认值（恒为 `NULL`），与 MySQL 不一致。已补 `DEFAULT (datetime('now','localtime'))`。

### 折叠机制

折叠阈值集中在 `db.py` 的 `FOLD_DONE_DAYS = 1`，改天数只动这一处。

「已折叠」= `level == 'done'`（截止时间已过）且已过期超过 1 天。分区由 SQL 完成，不重不漏：

| | 查询条件 | 用在哪 |
|---|---|---|
| 未折叠 `list_active` | `deadline IS NULL OR deadline > 分界线` | 首页默认渲染、管理页列表 |
| 已折叠 `list_folded` | `deadline <= 分界线` | 仅点击展开时请求 |

计数用独立的 `count_active` / `count_folded`（只 `SELECT COUNT(*)`），
所以首页折叠条上的条数**不需要查明细**；`/api/counts` 给管理页页签角标用，同样只查计数。

接口：
- `GET /api/notices?category=notice` → 未折叠部分（含全部置顶项）
- `GET /api/notices?category=notice&folded=1` → 已折叠部分（懒加载）
- `GET /api/counts` → 各分类的「进行中 / 已折叠」条数
- `PUT /api/notices/{id}/pin`，请求体 `{"pinned": true|false}` → 置顶/取消置顶，返回 `{ok, pinned, category_name, displaced}`（`displaced` 为被顶替掉的条数）

前端懒加载状态各自独立记忆：折叠区加载过一次就不再重复请求；收起再展开也不重新请求。
换分类、新增、删除折叠区的项时会重置标记，保证数据不陈旧。

### 首页模板重构

三个栏目的卡片原本是三段几乎重复的模板代码，已抽成 Jinja 宏 `item_card` / `item` / `fold_bar`。
`static/app.js` 里的 `FoldManager.renderItem` 输出结构与宏保持一致（含 `link` 包裹）。
前端渲染折叠内容时，`link` 只接受 `http(s)://` 开头的地址，`javascript:` 之类的会被忽略。

### 优先级规则（`db.py` 的 `compute_level`）

`level` 不再存库，每次查询按 deadline 与当前时间现算：

| 分类 | 紧急阈值 | 规则 |
|---|---|---|
| 班级通知 `notice` | 24 小时 | 距截止 ≤ 24h → 紧急；> 24h → 普通 |
| 作业提醒 `homework` | 24 小时 | 距截止 ≤ 24h → 紧急；> 24h → 普通 |
| 网课提醒 `online` | 72 小时 | 距截止 ≤ 72h → 紧急；> 72h → 普通 |
| 任意分类 | — | **截止时间已过 → 已完成** |
| 任意分类 | — | 未填截止时间 → 普通（无法判断，按最低紧急度） |

阈值集中在 `db.py` 的 `URGENT_HOURS` 字典，以后要改只动这一处；管理页的判定说明和前端预览都从后端注入，不会两处不同步。

**排序**：未过期按截止时间由近到远 → 未填时间的排其后 → 已完成的沉底（最近过期的在前）。

**倒计时**：首页卡片和管理列表都会显示「剩 X天X小时」或「已过 X小时X分」，由 `_duration_text` 统一格式化。

管理页新增表单在选完分类和截止时间后，会实时预览判定结果（与后端同一套规则的前端实现），避免填错才发现。

### 数据库变更

`notices` 表新增 `deadline` 列（MySQL `DATETIME`，SQLite `TEXT`）。
`db.py` 的 `_migrate()` 会在启动时自动检测并补列，**旧库升级无需手工执行 SQL**。
旧的 `level` / `sort_weight` 列保留但不再写入，仅为兼容旧库存在，可以不管。

## 二、服务器上启用 MySQL

1. 安装依赖：
   ```
   pip install -r requirements.txt
   ```
2. 在 MySQL 里建一个空库（表会自动创建，无需手动建表）：
   ```sql
   CREATE DATABASE classroom DEFAULT CHARSET utf8mb4;
   ```
3. 配置连接信息。**账密只从 `db.conf` 读取**（代码里已不留任何默认账号密码，
   也不再读环境变量）。在项目根目录（`main.py` 同目录）新建 `db.conf`：
   ```ini
   [mysql]
   host     = 127.0.0.1
   port     = 3306
   user     = 你的数据库用户名
   password = 你的数据库密码
   db       = 你的数据库名
   ```
   - `user` / `password` / `db` 三项必填，缺任意一项启动时会明确报
     `db.conf 缺少配置项：...`，而不是拿空值去撞 1045。
   - `db` 也可写成 `database`，两个键名都认。
   - 没有 `db.conf` 时自动降级到本机 SQLite（见第三节）。
4. 重启项目（gunicorn 配置沿用原 `gunicorn_conf.py`，无需改）。

启动后访问：
- 首页：`http://你的域名/`
- 管理后台：`http://你的域名/admin`

### 为什么只用 db.conf，不用宝塔环境变量

宝塔「Python 项目」面板里设的环境变量，**经常传不到 gunicorn worker**
（worker 是 gunicorn 自己 fork 的，不一定继承面板注入的 env）。
结果程序读不到你设的值，退回到默认值，就可能出现下面这种报错：

```
未连接 MySQL（OperationalError: (1045, "Access denied for user 'root'@'localhost' (using password: NO)"))
```

配置文件由程序自己从磁盘读，不受进程继承影响，因此更可靠。

### 报错速查

降级提示条会带上**实际生效的配置**，例如：
```
OperationalError: (1045, ...)  [user=sqlitshawn, host=127.0.0.1:3306, db=sqlitshawn, password=已填]
```

| 报错里看到的 | 说明 | 怎么办 |
|---|---|---|
| `Error: Already closed` | 建表其实成功了，但旧代码在 `with conn` 之后又关了一次连接，异常被误判为"连不上" | **已修复**：改用 `_safe_close` 幂等关闭。确认服务器上的 `db.py` 是最新版 |
| 用户名是 `root`，但你配的是别的账号 | 配置没生效，跑的是旧代码 | 重新上传 `db.py` 和 `db.conf`，确认与 `main.py` 同级，重启项目 |
| `using password: NO` / 提示"password=未填" | `db.conf` 里 `password` 没值 | 补上密码并重启 |
| `db.conf 缺少配置项` | 文件缺失或 user/password/db 有空项 | 按上面的模板补齐 |
| 账号密码都对仍报 1045 | 密码错了，或该账号没有这个库的权限 | 在宝塔 MySQL 里核对账密，并给该账号授予对应库权限 |

> ⚠️ 安全提醒：账密只放在 `db.conf`，代码里已无明文密码。请确认 `db.conf`
> 不会被提交到公开仓库（必要时加进 `.gitignore`），并把文件权限收紧为 `600`。

### 关于「服务器跑的是旧代码」

如果你已经上传了新 `db.py`，但报错里的用户名仍是 `root`（而新代码默认是 `sqlitshawn`），
说明**服务器上实际运行的还是旧文件**——新 `db.py` 没传上去，或传到了别的目录。
重新上传覆盖 `/www/wwwroot/my_fastapi/db.py`，并重启项目即可。

## 六、待办提醒

管理页目前**完全无鉴权**，任何知道 `/admin` 地址的人都能增删事项。
上线后建议至少加个基础密码或 IP 限制。

接龙页同理：**任何人都能填个名字报名**（这也是接龙的正常用法），
但没有登录就意味着"名字"是谁无法核实，且同名只允许报一次。
注意「只允许报一次」卡的是**姓名**，不是设备：同一台设备（同一个 cookie）
可以连续替多位同学代报名，条数不限 —— 页面上的提示与 `_preview/check_api.py` 都按这个规则写死。
v1.8.0 起姓名限制在 4 个字、附加信息限制在 20 个字：这是为了让名单一行放得下、一屏能扫完，
不是安全措施（真要防刷，得按上面说的加口令）。
如果以后要求实名，最省事的做法是给接龙表单加一个班级口令（写在 `db.conf` 里，
接口比对后再入库），不需要引入整套账号体系。

接龙的「附加信息」只做了**格式收口**（选「进行选择」时必须是候选项之一），
候选项是明文存储的，管理页改了候选项也不会影响已经报名的历史记录 ——
名单里存的是当时那一项的文字，属于预期行为。

v1.9.0 起**截止时间一过就不再收新的报名**（`db.rollcall_open`）。这条规则依赖
"事项的截止时间"这一个字段，所以：想让接龙一直开着，就**不要给这条事项填截止时间**；
截止时间同时也是首页级别（紧急 / 普通 / 已完成）与折叠的依据，两者共用同一个字段，
管理页改截止时间等于同时改了这两件事。撤销不受这条规则限制。
